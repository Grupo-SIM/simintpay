# Webhook queues

Webhook consumers use RabbitMQ through `RABBITMQ_URL` (local default: `amqp://localhost:5672`). The deployment Compose file includes a persistent RabbitMQ service; set `RABBITMQ_PASSWORD` to a strong URL-safe password before starting it. No broker port is exposed externally.

Queues and messages are durable/persistent. HTTP handlers wait for publisher confirmation, with a 10-second publication timeout. Direct DOM ingress opts into its idempotent consumer as a local fallback: when the broker is disconnected, or publishing fails, the HTTP request processes the webhook against the database before responding. Processing failures still propagate to the caller for retry; other queues retain their durable publication behavior. A timed-out publication can arrive later, so event signatures and atomic settlement guards remain required. Broker connect/disconnect/failure events and fallback activation are logged without credentials. Consumers acknowledge only after processing succeeds. Connection setup restores queues and consumers on reconnect. Each queue uses prefetch 1 to preserve transaction ordering; Zero Grau notifications run in `zero-grau-payment-notifications`, separately from DOM persistence.

Failed processing is retried up to three attempts, then retained in `<queue>.failed`. Inspect and fix the underlying failure before manually replaying messages. Failed/unprocessed webhook event records can be resumed; processed signatures remain idempotent. Notification requests time out after five seconds. Missing notification configuration skips delivery as before.

SimIntPay starts DOM polling at application bootstrap, logs `[Reconcile][poll] registered`, and immediately checks pending DOM payments created in the last 30 minutes, then repeats every five seconds. Polling uses its own overlap guard, independently of manual paginated reconciliation. Direct checks prefer the charge's integration/seller credential before the master fallback. Logs include selection counts, DOM status, request duration, webhook outcome and skipped runs.

SIM Delivery polls pending PIX and credit-card payments every five seconds, including when checkout is closed. Legacy Zero Grau card/PIX status and merchant-scoped status checks query DOM and reprocess paid results through the SimIntPay webhook before returning the persisted local status. Targeted checks have no 30-minute creation cutoff. Approval is never reported solely from a gateway response when local settlement failed. Token-authenticated merchant status checks are exempt from the shared IP throttle so several concurrent checkouts do not consume each other's polling allowance.

Delivery SSE connections re-read persisted payment status every five seconds, covering webhooks handled by another replica. PIX and card checkout also poll status with a ten-second request timeout, bypasses browser caches and refreshes on focus/reconnect. These intervals do not guarantee confirmation within five seconds when DOM requests or local processing fail.

Card creation no longer masks an approved or rejected gateway response as unconditional `PENDING`: it reconciles the linked transaction and returns its persisted status. Asynchronous authorization remains pending; settlement failures preserve the charge reference for later retries.
